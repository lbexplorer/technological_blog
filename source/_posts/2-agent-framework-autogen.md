本文记录一次基于 AutoGen 的多智能体开发框架学习：通过代码组织多个 LLM 角色之间的对话流转，模拟一个由产品经理、工程师、代码审查员和用户代理组成的软件开发团队。

## 任务目标

本次实验的目标是使用 AutoGen 构建一个模拟的软件开发团队。这个团队由多个具备不同职责的智能体组成，它们围绕一个真实的软件开发任务进行协作，并按照需求分析、代码实现、代码审查和执行验证的流程完成交付。

这个例子的核心不是生成某一段代码本身，而是观察多智能体系统如何通过角色分工和流程编排，把一个模糊任务拆解成可执行的协作过程。

## 原理分析

AutoGen 的关键能力在于用代码管理多个智能体之间的对话。每个智能体并不是简单地调用一次大模型，而是被赋予明确的角色、任务边界和协作方式。

### 1. 用系统消息定义智能体

定义智能体的核心在于编写高质量的系统消息（System Message）。

系统消息相当于智能体的行为准则和专业知识库，它需要明确说明智能体的角色、职责、工作流程，以及与其他智能体交互时应该遵循的规则。系统消息写得越清晰，智能体在多轮协作中的行为就越稳定。

在这个案例中，我们通过系统消息定义了多个角色。例如，`ProductManager` 负责需求拆解，`CodeReviewer` 负责质量审查。这样的角色划分能让不同智能体在协作中各司其职，减少输出混乱。

### 2. 用角色专业化降低复杂度

AutoGen 允许通过系统消息为每个智能体赋予专业化能力。一个智能体可以专注于产品需求，另一个智能体可以专注于代码实现，第三个智能体则关注可读性、健壮性和潜在缺陷。

这种设计的好处是：复杂任务不再由一个大模型一次性完成，而是被拆解成多个由领域“专家”处理的子任务。只要角色边界清晰，智能体提示词也可以在不同项目中复用，后续维护和扩展会更方便。

### 3. 用群聊机制组织协作流程

对于软件开发这类流程相对固定的任务，可以使用 `RoundRobinGroupChat` 这样的轮询群聊机制。

轮询机制的优点是流程清晰、顺序可预测。每个智能体按照既定顺序发言，系统可以稳定地经历“需求分析 -> 编码 -> 审查 -> 执行验证”的过程。

同时，`UserProxyAgent` 提供了“人类在环”（Human-in-the-loop）的接口。用户可以发起任务、观察中间结果，也可以在关键节点介入确认或调整方向。

### 4. 用异步主流程启动系统

AutoGen 0.7.4 采用异步架构，因此整个协作流程通常会放在一个异步函数中启动，并最终通过 `asyncio.run()` 执行。

这种方式适合处理多智能体对话、流式输出、工具调用和代码执行等过程。主流程负责串联模型配置、智能体定义、团队编排和最终运行。

## 智能体设计

为了模拟真实的软件开发流程，本次实验设计了四个职责分明的智能体角色：

| 智能体 | 职责 |
| --- | --- |
| `ProductManager` | 将用户的模糊需求转化为清晰、可执行的开发计划。 |
| `Engineer` | 根据开发计划编写具体的应用程序代码。 |
| `CodeReviewer` | 审查工程师提交的代码，关注质量、可读性和健壮性。 |
| `UserProxy` | 代表最终用户发起任务，并负责执行、验证最终交付结果。 |

这种角色划分是多智能体系统设计中的关键一步。它把一个复杂的软件开发任务拆成多个阶段，让每个阶段由更适合的智能体完成。

## 项目目录设计

示例项目可以按如下方式组织：

```text
multi_agent_dev_team/
├── main.py
├── agents/
│   ├── prompts.py
│   └── __init__.py
├── config/
│   └── model_config.py
├── workspace/
│   └── generated_project/
├── logs/
│   └── run_log.md
├── AGENTS.md
├── requirements.txt
└── README.md
```

各目录和文件的职责如下：

- `main.py`：负责整体流程编排，包括智能体创建、团队组装和任务启动。
- `agents/prompts.py`：保存各个智能体的系统提示词，方便统一维护。
- `config/model_config.py`：保存模型配置，避免把模型参数散落在业务代码中。
- `workspace/generated_project/`：保存工程师智能体生成的项目代码。
- `logs/run_log.md`：记录每轮智能体输出，便于复盘和展示。
- `requirements.txt`：记录 Python 依赖。
- `README.md`：说明项目用途、运行方式和目录结构。

## 智能体工作流

软件开发任务通常具有比较明确的阶段：需求分析、实现、审查和测试。因此，这里采用 `RoundRobinGroupChat` 来组织轮询式协作流程。

整体流程如下：

```text
用户输入开发任务
        ↓
UserProxyAgent 接收需求
        ↓
ProductManager 分析需求并生成开发计划
        ↓
Engineer 编写代码
        ↓
CodeReviewer 审查代码
        ↓
CodeExecutorAgent 执行代码 / 测试代码
        ↓
UserProxyAgent 输出验收结论
```

其中，`CodeExecutorAgent` 可以看作执行与验证环节的工具型角色。它不一定参与需求讨论，但在生成代码后负责运行代码、反馈错误信息，并帮助团队进入下一轮修正。

## 小结

AutoGen 的价值不只是“让大模型写代码”，而是把多个 LLM 角色组织成一个可编排、可观察、可扩展的协作系统。

这次实验可以总结出几点经验：

1. 系统消息决定了智能体的行为边界，是多智能体系统稳定运行的基础。
2. 角色拆分可以降低复杂任务的组织难度，让每个智能体专注于更明确的问题。
3. `RoundRobinGroupChat` 适合需求、编码、审查、验证这类线性流程。
4. 异步主流程和流式输出能提升调试体验，便于观察智能体之间的真实协作过程。

后续如果继续扩展，可以进一步加入更严格的代码执行环境、测试用例生成、日志分析和任务终止条件，让这个模拟团队更接近真实的软件工程工作流。
