## 引言

一个研究助手今天知道你在读 Agent Memory 的论文，下周却需要你重新解释研究目标；一个编程智能体刚修好测试配置，下次又重复同样的错误。这些现象指向同一个问题：过去的交互没有被组织成下一次可以使用的状态。

本文主要讨论 **LLM 智能体的外部、可更新记忆**。这里的记忆包含保存、组织、检索和使用历史信息的一整套机制。它可以存放用户偏好、任务进展、工具执行结果，也可以保存从失败中总结的经验。

本文是入门性质的研究笔记，选择 2023—2025 年的代表工作建立阅读路线，不作为截至发布日期的完整论文清单。文中的流程图为本站绘制的概念示意，工程建议与论文结论分别标明。

## 基本概述

### Memory、Context 与 RAG

**Context（上下文）** 是模型这一次调用实际看到的输入。历史记录即使已经保存到磁盘，如果没有被选入上下文，也不会自动参与本次回答。

**Memory（记忆）** 负责决定哪些信息跨轮次保存、怎样更新，以及什么时候重新拿出来。可以把它理解为上下文的一个可持续维护的信息来源。

**RAG（检索增强生成）** 是从外部资料检索证据，再用于生成的模式。记忆系统可以使用 RAG 读取历史，但还需要处理写入、去重、冲突、时间和删除。外部文档检索与个人交互记忆可以共用检索技术，信息来源和更新规则却可能不同。这是本文用于设计系统的区分方式，并非互斥的学术分类。

| 概念 | 主要问题 | 例子 |
| --- | --- | --- |
| 当前上下文 | 这一次模型能看到什么？ | 当前问题、最近对话、工具结果 |
| 持久记忆 | 哪些历史值得保存和重新使用？ | 用户更正过的偏好、项目状态 |
| 文档检索 | 从哪里找到回答需要的外部证据？ | 技术文档、论文、知识库 |
| 参数知识 | 模型训练后编码了哪些规律？ | 语言能力、通用知识；通常不随单次对话直接更新 |

### 更长的上下文能解决什么

更大的窗口可以容纳更多历史，但“放得下”不等于“总能正确使用”。旧信息和新信息冲突时，系统仍要识别时间；需要删除内容时，也不能只依赖截断。长上下文是值得比较的基线，记忆系统的价值则应通过回答质量、延迟和成本一起验证。

[LongMemEval](https://arxiv.org/abs/2410.10813) 将信息更新、时间推理和拒答纳入测试，提醒我们关注“记得对不对”，而不只是保存了多少文本。

## 记忆分类

下表采用面向实现的整理方式。不同系统的命名与边界不完全一致，短期／长期描述保存范围，情节／语义／程序描述内容用途，两者可以交叉。

| 类型 | 保存的内容 | 典型用途 | 主要风险 |
| --- | --- | --- | --- |
| 工作记忆 | 当前任务、近期对话、待执行步骤 | 保持这一轮任务连贯 | 超出窗口、任务状态丢失 |
| 情节记忆 | 某次交互或工具执行的经历 | 回答“上次发生了什么” | 缺少时间和来源 |
| 语义记忆 | 从经历中提取的事实、偏好与关系 | 个性化回答、事实复用 | 把推测固化为事实 |
| 程序记忆 | 可复用的步骤、策略和经验 | 避免重复试错 | 把偶然成功当通用规则 |

例如，在一个论文助手中，“今天检索了 MemGPT”是一条事件；“用户希望先看架构图”可能是一条偏好；“对比实验前先统一模型和 token 预算”则是一条流程经验。它们应携带不同的有效范围，不能因为都能写成文本就采用完全相同的更新策略。

## 记忆的工作流程

### 写入：从交互到候选记忆

建议先保留来源，再提取候选事实。用户明确表达的长期偏好、已确认的任务状态和可靠的工具结果，通常比一次性闲聊更适合复用。模型猜测应与用户确认的信息区分，不能直接升级为用户事实。

写入也不必都在回答前发生。与当前决策相关的状态可以同步处理，其余整理工作可以在回合结束后完成。选择同步还是异步，需要考虑一致性需求和实际延迟。

### 组织：摘要、索引与关联

原始记录便于回溯，摘要节省上下文，结构化字段方便过滤，关系链接方便跨记录探索。它们可以组合，但摘要或关系生成可能引入错误，因此应该保留到原始证据的引用。

不要把“更复杂的数据库”直接当作更好的记忆。对于少量用户偏好，结构化记录可能已经足够；需要跨事件关联时，再评估图结构或层级索引。

### 读取：检索之后还要选择

工程上可以先按用户、项目、时间与权限缩小范围，再进行关键词或向量检索，最后筛选和重排候选。被选中的证据应控制在预算内，并携带时间、来源和有效状态。

相似度只说明文本是否接近，不能单独证明内容仍有效。例如“以前使用 Windows”和“现在迁移到 Linux”可能都与环境问题高度相似，但回答“现在用什么系统”时，不能忽略更正关系。

### 更新与遗忘：让状态跟上变化

新事实可能补充旧事实，也可能取代旧事实。建议显式记录替代关系，避免把不同时间或不同项目的事实误判为冲突。删除时要覆盖原文、摘要、索引和派生缓存，否则删掉一条记录后，旧内容仍可能被检索出来。

## 代表论文阅读

以下按研究切入点梳理五篇论文。每篇重点记录“解决的问题—核心机制—阅读时的问题”，便于继续深读。

### Generative Agents：经历、反思与计划

<div class="memory-paper-meta">2023 · 行为模拟 · <a href="https://arxiv.org/abs/2304.03442">原论文 ↗</a></div>

**解决的问题：** 如何让模拟角色的行为与过去的经历保持关联，而不是每一轮都重新生成一个孤立动作？

**核心机制：** 系统以自然语言记录经历，逐步形成更高层次的反思，并动态检索记忆来规划行为。论文将这一架构用于一个包含 25 个智能体的交互式小镇，评估角色行为及群体互动的可信程度。

**阅读重点：** 留意原始观察和反思的区别：反思是对记录的归纳，不能视作新的独立观察。该工作的评价目标是行为模拟的可信度，不能直接等同于个人助手的事实记忆准确率。

### Reflexion：把失败反馈留给下一次尝试

<div class="memory-paper-meta">2023 · 反馈学习 · <a href="https://arxiv.org/abs/2303.11366">原论文 ↗</a></div>

**解决的问题：** 智能体如何在多次尝试中使用失败反馈，而不必每次都更新模型权重？

**核心机制：** 将任务反馈转换成文字反思，并放入情节记忆缓冲区，在后续尝试中辅助决策。这是一种通过语言反馈改进行为的方式，不是常规的梯度训练过程。

**阅读重点：** 检查反馈从哪里来、是否可靠，以及反思是否真正改变下一次行为。一个合理但错误的自我解释，也可能导致后续尝试沿错误方向继续。

### MemGPT：管理有限窗口与外部存储

<div class="memory-paper-meta">2023 · 分层上下文 · <a href="https://arxiv.org/abs/2310.08560">原论文 ↗</a></div>

**解决的问题：** 当历史对话或文档超过模型窗口时，如何决定哪些信息驻留在当前上下文，哪些放在外部？

**核心机制：** 借鉴操作系统的分层内存思想，在不同存储层之间移动信息，并通过控制流机制管理交互。论文在长文档分析与多会话对话场景中进行评估。

**阅读重点：** “虚拟上下文”不意味着底层模型拥有无限窗口。它把部分困难转移到了信息调度：该读什么、何时写回、错误调用怎样恢复。

### A-MEM：让笔记之间形成可演化的连接

<div class="memory-paper-meta">2025 · 关联组织 · <a href="https://arxiv.org/abs/2502.12110">原论文 ↗</a></div>

**解决的问题：** 固定的存储结构与检索操作，是否限制了记忆适应新经历的能力？

**核心机制：** 受 Zettelkasten 笔记方法启发，为新记忆生成包含上下文描述、关键词、标签等属性的笔记，分析它与历史记忆的联系，并允许新信息推动旧记忆表示的演化。

**阅读重点：** 关联结构是模型构建的组织方式，不是已经验证的因果图。实际应用还需观察错误关联、更新成本，以及更新后是否更容易检索到可靠证据。

### Mem0：面向持续对话的提取与整合

<div class="memory-paper-meta">2025 · 对话记忆 · <a href="https://arxiv.org/abs/2504.19413">原论文 ↗</a></div>

**解决的问题：** 如何在多会话对话中保留重要信息，同时减少每次携带全部历史的开销？

**核心机制：** 从持续对话中动态提取、整合和检索显著信息，并进一步研究图结构记忆变体。论文基于 LoCoMo 比较不同方案，讨论回答表现、延迟和 token 成本。

**阅读重点：** 性能数字依赖具体模型、评测题型、历史切分和裁判配置。复现时应同时比较质量与资源开销，不把论文中的相对提升直接视为所有应用都能获得的收益。

### 如何比较这些路线

| 工作 | 主要切入点 | 适合追问的问题 |
| --- | --- | --- |
| Generative Agents | 经历与反思支持行为 | 归纳出的反思是否有原始证据？ |
| Reflexion | 反馈指导再次尝试 | 记下教训后，重复错误是否减少？ |
| MemGPT | 上下文与存储分层 | 调度错误和额外调用的代价是什么？ |
| A-MEM | 记忆组织与演化 | 新关联是否改善有效证据的召回？ |
| Mem0 | 对话信息提取与整合 | 相同质量下能否降低 token 和延迟？ |

这些工作解决的任务并不完全相同。表格是阅读路线，不是同一排行榜上的性能排序。

## 数据集与评估指标

### LoCoMo：跨会话的长期对话

[LoCoMo](https://arxiv.org/abs/2402.17753) 提供长期、多会话对话，覆盖问答、事件总结和多模态对话生成。它适合观察模型能否使用跨时间分布的线索，而不只是在最近一轮复述内容。

使用时应明确采用哪一项任务、哪种问题子集和评分方式。同样写着“在 LoCoMo 上测试”，不代表评测协议完全相同。

### LongMemEval：更新、时间与拒答

[LongMemEval](https://arxiv.org/abs/2410.10813) 包含 500 个问题，覆盖信息提取、多会话推理、时间推理、知识更新与拒答五类能力。论文还从索引、检索和阅读三个阶段分析记忆系统。

它对工程实现的启发是：不应只测试“能否回忆到旧信息”，还要测试“能否采用更新后的信息”，以及“没有证据时是否知道不回答”。

### 一张更实用的评估清单

下面是本文建议的工程指标，不是上述基准统一规定的指标。

| 维度 | 建议观察 | 一个测试例子 |
| --- | --- | --- |
| 回答正确性 | 有证据支持的答案比例 | 从多次会话还原最终项目要求 |
| 检索质量 | 相关证据召回、无关信息比例 | 检查关键更正是否进入候选集 |
| 时效与冲突 | 新旧事实选择是否正确 | 偏好变化后不继续使用旧偏好 |
| 拒答与隔离 | 无证据时拒答、跨用户泄漏 | 用户 B 不应召回用户 A 的记录 |
| 资源消耗 | 写入／读取延迟、token、存储 | 将记忆整理成本也计入总成本 |
| 删除一致性 | 原始与派生数据是否都失效 | 删除后再查询原事实 |

## 工程实践：一个最小记忆闭环

### 为一条记忆保留必要元数据

以下是说明数据结构的虚构示例，不是某个框架的 API。时间范围用于描述事实何时有效，来源用于追溯，状态用于区分当前记录与已被替代的记录。

```json
{
  "id": "mem_demo_002",
  "namespace": "demo-user/research-project",
  "type": "semantic",
  "content": "论文解读优先给出架构图和关键假设",
  "source": {"session_id": "session_demo", "message_id": "msg_12"},
  "evidence": "用户明确表达",
  "valid_from": "2026-09-14",
  "valid_to": null,
  "status": "active",
  "supersedes": "mem_demo_001"
}
```

### 先建立基线，再增加复杂度

建议在相同模型和任务集下，依次比较：只保留最近对话、在预算内输入完整历史、检索原始历史、加入结构化记忆。这样才能知道改进来自记忆设计，还是仅仅来自更多输入或更多模型调用。

一次读取可以拆成下面的伪代码。每个函数表示一个职责，需要应用自行实现；它不是开箱即用的 SDK 示例。

```text
scope = authorize(user, project)
candidates = retrieve(query, scope, status="active")
evidence = rerank_and_select(candidates, token_budget)
answer = generate(query, recent_context, evidence)

proposals = extract_candidates(user_messages, verified_tool_results)
validated = check_sources_and_conflicts(proposals, scope)
commit_updates(validated)  # 保留版本和证据；不直接保存模型猜测
```

### 三类值得提前发现的失败

**记错：** 摘要把“可能迁移到 Linux”写成“已经迁移”。需要区分计划、推测和已确认状态，必要时回看原始消息。

**用错：** 检索命中了正确用户的旧项目，却用于当前项目。除了语义相似度，还需要项目范围与时间约束。

**信错：** 工具输出或网页里夹带“忽略之前规则”一类指令，被写入长期记忆后反复影响行为。检索出来的内容应当作为待判断的资料，不能因为被存储过就提升为系统指令。

## 总结与后续阅读

设计记忆系统时，可以沿着三个问题往下看：**保存了什么证据，怎样维护变化，最终是否改善决策。** 向量检索、摘要和知识图谱都是可用组件，是否需要它们，应由任务与评测结果决定。

初次阅读可以先用 Generative Agents 理解“经历—反思—行为”，再读 MemGPT 的分层管理，然后对照 A-MEM 与 Mem0 的组织方式。若关心智能体反复试错，则单独阅读 Reflexion；开始实现后，用 LoCoMo 和 LongMemEval 检查评测盲区。

后续值得继续补充的方向包括：多智能体之间的记忆共享与权限边界、多模态事件的存储方式，以及记忆压缩后的证据保真性。
